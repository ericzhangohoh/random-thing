# HiMCM 2018 A: five complete-paper comparisons for ranking and recommendation workflows

Evidence depth: all five locally archived 2018 A papers have been read in full, including their appendices, with image/formula gaps inspected visually. This does not mean their numerical outputs have been reproduced. Physical PDF page references and scope qualifications are in the linked individual reviews. Award classifications remain inherited mirror metadata, not independently verified award evidence.

## The common demand and the real decision

The official prompt asks for a specification-only descriptive ranking, a top ten, comparison against two online rankings, an app concept and one-page news release. It explicitly supplies imperfect data and a selected subset of operating coasters. The task therefore contains two different decisions: what a generic specification ranking means, and which ride a particular person might prefer. The five papers approach this distinction differently.

| Paper | Main architecture | Strongest explicit justification | Main limitation that changes how to reuse it |
|---|---|---|---|
| [8554](../reviews/himcm/HIMCM_2018_A_8554.md) | Cluster-assisted imputation → experience indicators → entropy/default or preference/personal score | Similar designs motivate local imputation; the same indicator layer supports multiple preference profiles (pp.5–12). | Missingness and encoding assumptions dominate; entropy weighting does not make enjoyment objective. Published score ranges do not follow the stated bounded aggregation. |
| [8700](../reviews/himcm/HIMCM_2018_A_8700.md) | Neural imputation → feature screening/entropy → separate fuzzy and collaborative/tag recommender | Choosing ItemCF is connected to a stable, small item universe relative to users (pp.28–30); alternatives to entropy are discussed (p.16). | Several advertised transformations do not clearly connect to output; printed code and feature-selection prose diverge. Imputation error is not clearly an out-of-sample percentage. |
| [8744](../reviews/himcm/HIMCM_2018_A_8744.md) | Incremental thrill score − nonlinear discomfort penalties → survey/AHP weights | A highly thrilling ride can also be unpleasant, so benefit and discomfort need separate components (pp.10–18). | Forum/survey preferences enter the purported objective baseline; physiology-to-ride transfer lacks calibration; code includes a length term absent from the final equation. |
| [8874](../reviews/himcm/HIMCM_2018_A_8874.md) | Physical/statistical completion → fuzzy preference + entropy blend → clipping revision | Fuzzy intervals express uncertain relative judgments; logarithms simplify ratio optimization (pp.10–15). | Removing clipping is motivated by the same external lists later cited as validation. Sensitivity code accumulates changes instead of resetting the baseline. |
| [8992](../reviews/himcm/HIMCM_2018_A_8992.md) | Dependency-ordered linear imputation → three grouped scores → shared general/personal engine | Grouping reduces 28 user comparisons to three, while the same scoring engine supports both flows (p.22). | Training fit does not validate imputation, group weights remain judgments, and code applies group-size division twice in the personalized example. |

## What the evidence supports for the agent workflow

1. **Frame the target before choosing a method.** Ask whether the output is descriptive performance, average preference or personal utility. A reader should see why a model with only specifications can answer the selected question. Do not let an entropy formula substitute for this argument. All five cases expose this boundary; 8992 gives the clearest explicit two-user framing (pp.5–6, 22).
2. **Make preprocessing part of the model.** Record which entries are observed, corrected, imputed or excluded. Missingness for G-force and angle is substantial, so a credible ranking needs more than a filled table. The dependency order in 8992 (pp.8–9) and subgroup reasoning in 8554 (pp.5–8) are useful templates. Neither removes the need for holdout errors and uncertainty propagation.
3. **Keep mechanisms, preferences and conventions separate.** Height, speed and drop are measurements; a mapping to thrill is a construct; 5:5:1 group weights, type scores, clipping bounds and sigmoid thresholds are assumptions or preferences. An agent must label the provenance of each instead of calling the full chain objective.
4. **Add complexity only for a named deficiency.** 8744's discomfort component addresses a clear failure of monotone thrill scoring. 8700's item/tag recommender has a different input requirement and purpose from its static specification ranking. Require each added method to declare its input, output, test and effect on a final deliverable.
5. **Tie tests to claims.** Training R-squared, matrix consistency, overlap with a popularity list, rank sensitivity and usability testing answer different questions. None substitutes for the others. Once external lists are used to tune the model, evaluate final generalization with separate evidence or say that only calibration agreement is available.
6. **Audit the executed expression.** These papers repeatedly contain mismatches between prose, final equations, appendices and output tables. A single frozen parameter/run record should generate all displayed numbers. A reviewer can identify many problems without rerunning a solver: score bounds, units, missing result cells, parameter dimensions, baseline resets and time-zero identities are inexpensive checks.

## Role contracts for this problem family

The problem analyst writes a demand-to-output table and a one-paragraph definition of the ranking construct. The data engineer delivers the cleaned data plus cell-level provenance, imputation dependency order and residual assessment. The modeler delivers a simple baseline, a candidate comparison and a parameter provenance table. The validator independently tests range/monotonicity, subgroup behavior, imputation uncertainty and top-k instability. The app designer uses the already-defined score engine and states which future data the concept would need. The writer distinguishes demonstrated results, design proposals and speculative explanations of external disagreement. The integrator rejects a final package when equations, code and reported rankings use different feature sets or transforms.

## A concrete justification pattern

“Users need [decision]. The available measurements capture [specified aspects] but omit [named aspects]. We therefore define [construct] and use [baseline] because [data/decision structure]. We add [extension] only to address [demonstrated deficiency]. Inputs [A] are measured, [B] are imputed and [C] are judgments. The validation establishes [bounded claim]; it does not establish [unmeasured claim]. Under [scenario range], the recommendation [does/does not] change.”

This pattern is an inference from comparative reading, not a quotation or a claim that any single paper fully satisfies it.
